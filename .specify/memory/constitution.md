# Generic Electron Launcher Constitution

## Core Principles

### I. 游戏包保持完整

必须通过游戏的原始入口启动，不得通过解包改写或重打包游戏实现兼容。游戏资源、包结构和引擎策略由适配边界表达，不作为共享核心的隐式前提。

### II. 用户数据安全

不同游戏的配置、运行状态、存档与测试数据必须有明确归属。不得静默删除、迁移、重置数据或更换其位置；未知已有数据和不兼容运行时必须安全拒绝。确需迁移时，先在 Feature Spec 明确恢复方案并验证数据保留。
测试只使用合成应用或用户明确授权的隔离副本，清理只能作用于测试创建的数据。

### III. 自动化验证

非平凡核心逻辑必须有小型自动化测试或断言，覆盖输入校验和失败边界。外部交互应可替换，不以真实游戏或剧情作为核心规则的唯一测试手段。
启动、窗口和数据行为改变时必须运行受影响的隔离回归；无法执行的检查如实记录，不能当作通过。

### IV. 最小实现与复用

新增游戏通过配置与明确适配复用同一核心，不能复制整套启动器。优先标准库、平台能力和现有模块；无已确认需求不建立插件平台、扩展协议或额外依赖。简化不得削弱错误处理、数据保护或通用行为。

### V. 可诊断与边界透明

失败应定位到目标游戏和处理阶段。记录实际运行时身份，区分进程存在、界面可用和完整流程验证。运行文档必须提供可复现方法及已知限制，不把单一夹具或样本成功推广为所有游戏兼容。

### VI. 核心解耦

共享核心不得判断游戏名称、个人安装目录或引擎内部对象。游戏专属初始化、权限、更新与补丁必须留在适配边界；不得从配置动态加载任意代码。没有私有默认游戏或内置个人数据。

### VII. 渐进变更

按可验证、可回退的小步骤实施；改变通用用户行为时明确原因、范围及恢复方法，不以整理架构为由一次性重写。用户明确移除的私有适配不属于公开版本的兼容承诺。

### VIII. 技术与公开资料连续性

沿用 JavaScript/CommonJS、现有构建交付方式和代码规范；迁移语言、框架或运行时必须有具体需求及验证依据。
公开仓库不包含玩家数据、运行时二进制、个人路径、账户信息、私有截图或凭据。发布审查必须覆盖 Git 历史和提交元数据，不能只检查工作树。

## 运行与验收

Constitution 只定义长期原则；版本识别、支持平台、配置格式和用户交互放在 Feature Spec，接口和实施步骤放在计划中。
每次实现检查核心/适配边界、用户数据、测试、公开文档及可回退性。具体游戏接入仍须核对其实际版本、主入口和存储规则，启动器不是未知代码的安全沙箱。

## Governance

本章程优先于旧模板。修订需说明原因和影响，并同步 Feature、模板及运行文档；例外不能由任务备注悄悄改变原则。
不兼容原则重定义升 MAJOR，实质扩展升 MINOR，措辞勘误升 PATCH。采纳日期保持不变，修订日期使用 ISO 8601。
用户明确授权的公开历史重建应先在仓库外保留私有备份，公开提交不得继续引用含敏感内容的旧历史。
